    8. 执行线程

    本章介绍在单个程序中同时执行多段代码：线程 （执行线程）以及用于同步它们的工具。大约二十年前，大多数机器只有一个处理器，并行在很大程度上是由操作系统营造的一种假象。如今，即使是最基本的笔记本电脑也有多个核心：多个线程确实在同时运行，这使得这里讨论的同步问题更加普遍。

    Java 从第一个版本（1996 年）起就支持线程：[Thread] 类、[synchronized] 关键字，以及 [wait] / [notify] 方法（属于 [Object] 类）。Java 5（2004 年）增加了 [java.util.concurrent] 包及其子包 [java.util.concurrent.locks] 和 [java.util.concurrent.atomic]：锁、信号量、并发集合、线程池等。Java 7 增加了 [Fork/Join] 框架，Java 8 引入了并行流，Java 21 引入了 虚拟线程，所有这些都深刻改变了服务器的编写方式。Java 25 终于引入了作用域值（[ScopedValue]）。我们将在本章探讨所有这些工具。

    这些示例是紧凑源文件（[java Threads01.java]），位于 [08-threads] 文件夹中。请记住，紧凑源文件会自动导入整个 [java.base] 模块：因此，包 [java.util.concurrent]、[java.util.concurrent.locks]、[java.util.concurrent.atomic] 和 [java.time] 中的类无需 [import] 指令即可使用。

    开始之前先提醒一句：多线程程序的结果每次运行都不尽相同。线程被分配处理器的顺序取决于操作系统、处理器数量和机器的负载。本章所示的结果是在一台与其他高度活跃的程序共享的双处理器 Linux 机器上得到的。如果您运行这些示例，会得到相似的结果，但很少会完全相同。我们会在每种情况下指出哪些是可重现的，哪些不是。

    8.1. Thread 类

    应用程序启动时，它运行在一个称为线程的执行流中。表示线程的 Java 类是 [java.lang.Thread] 类。它的主要构造函数和方法如下：

    [Thread] 类还有一个方法 [stop], 它过去用于强行终止线程。它自 Java 1.2 起就已弃用，自 Java 20 起，它只是抛出 [UnsupportedOperationException] 异常：突然停止线程可能会使它正在处理的数据处于不一致的状态。如今，我们请求线程 协作式地 停止，方法是 中断它：稍后我们会讨论这一点。

    8.2. 创建执行线程

    可以让应用程序中的各段代码在不同的执行线程中“同时”执行。如果机器的处理器数量少于准备执行的线程数，这些线程就会共享处理器：每个线程轮流使用处理器很短的一段时间（几毫秒）。在多处理器机器上，多个线程确实在同时执行。分配给线程的时间取决于多种因素，包括它的优先级，优先级有默认值，但可以通过编程方式设置（[setPriority]）；这只是一种参考，操作系统可以自由忽略它（Linux 默认会忽略它）。获得处理器的线程可以提前释放它：

    • 通过等待某个事件（使用 [join] 等待另一个线程结束，或等待信号）；
    • 通过休眠指定的一段时间（[sleep]）。

    线程 T 首先被创建，例如通过构造函数 [new Thread(task, name)]，其中 [task] 是实现函数式接口 [Runnable] 的对象，该接口唯一的方法是 [void run()]。这个对象通常是 lambda 或方法引用（函数式接口已在第 7 章介绍）。在较旧的代码中，您还可能遇到派生自 *[Thread]* 并重新定义其方法 *[run]* 的类：不推荐这样做，因为它把要执行的任务与执行任务的手段混在了一起。

    创建线程并不会启动它：

    • 线程 T 的执行由 [T.start()] 启动：传给 T 的构造函数的任务的 [run] 方法随后将由线程 T 执行。执行 [T.start()] 指令的代码不会等待线程 T 结束：它立即转到下一条指令。现在我们有两个线程在并行运行。它们常常需要彼此通信，以跟踪共同工作的进展：这就是线程 同步的问题；
    • 线程 T 一旦启动，就自主运行。当它正在执行的方法结束时，它就停止；
    • 我们可以使用 [T.join()] 等待它执行完毕。这是一条阻塞指令：执行它的线程会被阻塞，直到线程 T 完成它的工作。这是一种基本的同步方法。

    // 创建执行线程

void main() {
    // 我们为主线程命名
    Thread.currentThread().setName("Main");

    // 创建 5 个线程
    var tasks = new Thread[5];
    for (int i = 0; i < tasks.length; i++) {
        // 第 i 号线程将执行 display 方法，我们给它命名为 "i"
        tasks[i] = new Thread(this::display, String.valueOf(i));
        // 我们启动其执行（非阻塞操作）
        tasks[i].start();
    }

    // 主线程结束
    IO.println("End of thread " + Thread.currentThread().getName() + " at " + time());
}

// 线程执行的方法：它具有 Runnable.run() 的签名
void display() {
    // 执行该方法的线程
    Thread current = Thread.currentThread();
    IO.println("Start of execution of the display method in thread " + current.getName()
            + " (id " + current.threadId() + ") : " + time());
    // 休眠 1 秒
    sleep(1000);
    IO.println("End of execution of the display method in thread " + current.getName()
            + " : " + time());
}

// 休眠 [ms] 毫秒
static void sleep(long ms) {
    try {
        Thread.sleep(ms);
    } catch (InterruptedException e) {
        // 休眠被中断：我们恢复线程的中断标志
        Thread.currentThread().interrupt();
    }
}

// 当前时间，精确到毫秒
static String time() {
    return LocalTime.now().format(DateTimeFormatter.ofPattern("HH:mm:ss.SSS"));
}

    说明：

    • 第 5 行：我们给主线程起一个名字；
    • 第 8–14 行：创建并启动 5 个线程。它们的引用存储在一个数组中，以便以后取用。每个线程执行第 21–30 行的 [display] 方法；
    • 第 11 行：方法引用 [this::display] 会被自动转换为 [Runnable] 对象：方法 [display] 与 [run] 一样，没有参数也没有返回结果。我们写成 [this::display] 是因为在紧凑源文件中，声明在任何类之外的方法是隐式类的实例方法，而这个类的名称不能在代码中使用。构造函数的第二个参数是线程名称；
    • 第 13 行：启动线程 #i。该操作是非阻塞的：线程 #i 与启动它的主线程并行运行；
    • 第 17 行：主线程到达程序末尾；
    • 第 21–30 行：[display] 方法显示执行它的线程的名称和 ID，以及执行的开始和结束时间（精确到毫秒）；
    • 第 27 行：任何执行 [display] 方法的线程都会暂停 1 秒。处理器随后被交给另一个等待处理器的线程。1 秒的暂停结束时，暂停的线程重新有资格获得处理器。轮到它时，它就会获得处理器；
    • 第 33–40 行：方法 [sleep] 封装了 [Thread.sleep]。[Runnable] 中的方法 [run] 不声明任何受检异常：因此，[display] 方法不能让 [InterruptedException] 异常（由 [sleep] 抛出）逃逸出去。方法 [sleep] 会拦截它并重置线程的中断标志（第 38 行）；我们将在中断一节中解释这个操作。在本章的大多数程序中，我们都会遇到这个小方法；
    • 第 43–45 行：方法 [time] 以 [HH:mm:ss.SSS] 格式（[SSS]：毫秒）返回当前时间。

    // 守护线程

void main() {
    // 我们为主线程命名
    Thread.currentThread().setName("Main");

    // 线程构建器：平台线程、守护线程，命名为 0、1、2……
    Thread.Builder builder = Thread.ofPlatform().daemon().name("", 0);
    // 创建并启动 5 个守护线程
    for (int i = 0; i < 5; i++) {
        // start 创建线程并立即启动它
        builder.start(this::display);
    }

    // 我们给线程留出启动的时间
    sleep(100);
    // 主线程结束，因此程序也结束
    IO.println("End of thread " + Thread.currentThread().getName() + " at " + time());
}

// 线程执行的方法
void display() {
    Thread current = Thread.currentThread();
    IO.println("Start of execution of the display method in thread " + current.getName()
            + " : " + time());
    // 休眠 1 秒
    sleep(1000);
    IO.println("End of execution of the display method in thread " + current.getName()
            + " : " + time());
}

// 休眠 [ms] 毫秒
static void sleep(long ms) {
    try {
        Thread.sleep(ms);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}

// 当前时间，精确到毫秒

    说明：

    8.3. 停止线程：中断

    如何在线程完成工作之前停止它，例如当用户取消一个长时间运行的操作时？Java 不允许您杀死线程；相反，它提供了一种称为 中断的协作机制：

    • 每个线程都有一个 中断标志，这是一个布尔值，初始为 [false]；
    • 想要停止线程 T2 的线程 T1 调用 [T2.interrupt()]。这会设置 T2 的中断标志。这是一个终止 请求 ：T2 并未被终止；由该线程自己决定何时以及如何终止自己，以便让它的数据保持一致的状态；
    • 如果 T2 阻塞在某个等待方法中（[sleep]、[join]、[wait]，以及 [java.util.concurrent] 中的大多数阻塞方法），它就会被唤醒：该方法抛出 [InterruptedException] 异常，并且中断标志被重置为 [false]；
    • 如果 T2 执行的计算从不等待，它就必须定期使用 [Thread.currentThread().isInterrupted()] 检查自己的标志。

    这就是为什么阻塞方法要声明受检异常 [InterruptedException]：编译器要求程序员决定如何处理停止请求。有两种正确的响应：让异常传播给调用者（在 [throws] 子句中声明它），或者捕获它并干净利落地结束任务。当这两种做法都不可行时，比如上一个程序的 [sleep] 方法，就使用 [Thread.currentThread().interrupt()] 重新设置标志，这样调用方代码仍然能看到这个请求。唯一不正确的响应是忽略该异常。程序 [Threads05.java] 演示了这三种情况：

void main() throws InterruptedException {
    // 1 - 大部分时间处于休眠的线程
    Thread sleeper = Thread.ofPlatform().name("sleeper").start(() -> {
        int round = 0;
        try {
            while (true) {
                round++;
                IO.println(time() + " : sleeper, round " + round);
                // 如果线程在休眠时被中断，sleep 会抛出 InterruptedException
                Thread.sleep(400);
            }
        } catch (InterruptedException e) {
            // 中断是一个停止请求：线程干净地完成其工作
            IO.println(time() + " : sleeper interrupted while sleeping, it stops");
        }
    });

        long n = 0;
        // 线程定期检查其中断标志
        while (!Thread.currentThread().isInterrupted()) {
            n++;
        }
        IO.println(time() + " : calculator interrupted after %,d iterations, it stops".formatted(n));
    });
    // 3 - 忽略中断的线程（不要模仿）
    Thread deaf = Thread.ofPlatform().name("deaf").daemon().start(() -> {
        for (int i = 0; i < 10; i++) {
            try {
                Thread.sleep(400);
            } catch (InterruptedException e) {
                // 异常被“吞掉”了：停止请求丢失
                IO.println(time() + " : deaf ignores the interruption and continues");

        }

    Thread.sleep(1000);
    IO.println(time() + " : Main requests the three threads to stop");
    sleeper.interrupt();
    calculator.interrupt();
    deaf.interrupt();
    // 等待每个线程结束，最多等待 1 秒

        boolean finished = thread.join(Duration.ofSeconds(1));
        IO.println(time() + " : thread " + thread.getName() + " finished: " + finished);
    }
}

    8.4. 虚拟线程

    到目前为止我们创建的线程都是 平台线程：每一个都是对一个操作系统线程的封装，并在其整个生命周期内占用该系统线程。系统线程是一种昂贵的资源：创建它需要时间，它的栈会预留内存（大约一兆字节），而且系统无法高效地管理超过几千个这样的线程。然而，为每个客户端分配一个线程的服务器（见下一段中的图示）大部分时间都在等待：等待数据库的响应、等待客户端的下一个请求……在这些等待期间，系统线程被阻塞而无法使用。

    Java 21 引入了 虚拟线程 （“virtual threads”，JEP 444）。虚拟线程与其他任何对象一样是一个 [Thread] 对象，但它由 Java 虚拟机而不是操作系统管理：

    • 为了执行，虚拟线程被 挂载 到一个平台线程上，该平台线程称为它的“载体线程”。载体线程构成一个小型的池，其大小默认为处理器的数量；
    • 当虚拟线程阻塞时（[sleep]、等待网络 I/O、等待锁、阻塞队列等），它会被 卸载：它的栈被存放在虚拟机的内存中，载体线程立即可供另一个虚拟线程使用。当等待结束时，虚拟线程会重新挂载到某个宿主线程上——不一定是原来的那个；
    • 一个虚拟线程只占用几百字节：可以创建数百万个。

    long start = System.nanoTime();
    var threads = new ArrayList<Thread>(nbThreads);
    for (int i = 0; i < nbThreads; i++) {
        threads.add(builder.start(() -> sleep(1000)));
    }
    for (Thread thread : threads) {
        thread.join();
    }
    long duration = (System.nanoTime() - start) / 1_000_000;

}

    8.5. 线程的好处

    既然我们已经强调了存在一个默认线程——执行 [main] 方法的那个线程——并且知道了如何创建其他线程，让我们来考虑线程的好处。它们主要有两种用途：

    • 为耗时的计算利用 机器的 所有处理器 ：工作被划分成若干块，分配给不同的线程。我们将在本章末尾使用并行流和 [Fork/Join] 框架来做到这一点；
    • 同时执行多个任务，尤其是当其中一些任务主要涉及等待（等待网络响应、磁盘读取或用户输入）时。互联网上的客户端/服务器应用程序就是这种情况，我们将在第 12 章讨论。

    在客户端/服务器互联网应用程序中，位于机器 S1 上的服务器响应来自远程机器 C1、C2、……、Cn 上的客户端的请求：

    8.7.3. ReentrantLock 类

    [synchronized] 锁简单但不灵活：等待监视器的线程会无限期等待，既不能在一定时间后放弃，也不能被中断。[java.util.concurrent.locks.ReentrantLock] 类（Java 5）是一种显式锁——它同样是可重入的——提供了这些能力。它实现了 [Lock] 接口。我们将使用下面的构造函数和方法：

    成员
    作用
    [ReentrantLock()], [ReentrantLock(boolean fair)]
    创建一个锁。公平锁（[true]）按线程请求锁的顺序授予它；非公平锁（默认）更快，但线程可能插队到其他线程前面
    [void lock()]
    正在执行 [V.lock()], 的线程 T1 请求锁 V。如果 V 没有被任何线程持有，它就被授予 T1。如果线程 T2 随后执行同样的操作，它就会被阻塞：一个锁只能属于一个线程。当 T1 释放 V 时，T2 会被解除阻塞。因此，可能有多个线程在等待 V 时被阻塞

    8.7.4. 同步进程：文件锁

    上面描述的锁用于同步同一个虚拟机内的线程——即同一个进程内的线程。有时不同的进程需要共享某个资源，比如文件，或者您可能想防止同一个应用程序的两个实例被启动。Java 没有提供跨进程共享的具名同步对象；取而代之的是使用由操作系统管理的 文件锁 ：即 [java.nio.channels.FileLock] 类。锁是在以 [FileChannel] 通道形式打开的文件上获得的：

    • [FileLock lock()]：等待锁变为可用并获取它；

    8.7.7. 写入可见性：volatile 关键字

    锁并不只是用来使一组操作不可分割。它们还解决了第二个更隐蔽的问题：写入的 可见性 。为了加快速度，处理器会把值存储在它的寄存器和缓存中，而编译器会即时地重排或消除读写操作，正如我们在程序 [Threads09.java] 中看到的那样。因此，一个线程写入的值可能要过一段时间才会被另一个线程看到——或者可能永远都看不到。

    Java 内存模型 精确地定义了何时保证写入是可见的：当写入与读取之间存在“happens-before”关系时。主要的几种如下：

    • 线程在释放锁（[synchronized] 代码块结束、[unlock]）之前所做的一切，对随后获取该锁的线程都是可见的；
    • 调用线程在 [start] 之前所做的一切对被调用线程可见；一个线程所做的一切，对通过 [join] 等待它结束的线程可见；
    • 对 [volatile] 字段的写入，对该字段随后的任何读取都是可见的；
    • [java.util.concurrent] 中的工具提供类似的保证：线程在 [release()]、[countDown()], 或向并发集合插入元素之前所做的一切，对随后执行 [acquire()]、[await()], 或移除该元素的线程都是可见的。

// 启动所有执行 [increment] 共 nbIncrements 次的线程，然后显示 [value]
void measure(String method, Runnable increment, LongSupplier value) throws InterruptedException {
    Counter.reset();
    // 启动信号，使所有线程同时开始
    var start = new CountDownLatch(1);
    var threads = new Thread[nbThreads];
    for (int i = 0; i < nbThreads; i++) {
        threads[i] = Thread.ofPlatform().start(() -> {
            try {
                start.await();
            } catch (InterruptedException e) {
                return;
            }
            for (int j = 0; j < nbIncrements; j++) {
                increment.run();
            }
        });
    }
    // 出发！
    long begin = System.nanoTime();
    start.countDown();
    for (Thread thread : threads) {
        thread.join();
    }
    long duration = (System.nanoTime() - begin) / 1_000_000;
    IO.println("%-24s : obtained value %,12d in %5d ms".formatted(method, value.getAsLong(), duration));
}

    8.8. 并发访问多个共享资源

    8.8.1. 死锁

    在我们前面的示例中，不同的线程共享的是单个资源。如果有多个资源并且它们相互依赖，情况就会变得更复杂。尤其是可能发生死锁：两个线程互相等待。考虑下面依次发生的动作：

    • 线程 T1 获取锁 V1，以访问共享资源 R1；
    • 线程 T2 获取锁 V2，以访问共享资源 R2；
    • 线程 T1 请求锁 V2。它被阻塞；
    • 线程 T2 请求锁 V1。它被阻塞。

    线程 T1 和 T2 无限期地互相等待。有几种可行的解决方案：

    • 使用单个锁同时请求两个资源。如果这会导致对一个代价高昂的资源长时间加锁，这就并不总是可行；
    • 始终 按 相同的顺序获取锁：如果所有线程都先获取 V1 再获取 V2，就不可能发生死锁。这是最常用的规则；
    • 持有 V1 却无法获取 V2 的线程会释放 V1，以避免死锁。

// 获取第 1 个资源，然后在 [timeout] 内尝试获取第 2 个
static void work(Lock first, String firstName, Lock second, String secondName, Duration timeout) {
    String name = Thread.currentThread().getName();
    first.lock();
    try {
        IO.println(time() + " : " + name + " obtained " + firstName);
        // 我们给另一个线程留出获取其第一个资源的时间
        Thread.sleep(500);
        IO.println(time() + " : " + name + " requests " + secondName);
        // 带最长等待时间的请求，而不是会无限期等待的 lock()
        if (second.tryLock(timeout.toMillis(), TimeUnit.MILLISECONDS)) {
            try {
                IO.println(time() + " : " + name + " obtained " + secondName
                        + " and works with " + firstName + " and " + secondName);
            } finally {
                second.unlock();
            }
        } else {
            IO.println(time() + " : " + name + " did not obtain " + secondName + " within " + timeout.toSeconds()
                    + " s: it releases " + firstName + " and gives up");
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        first.unlock();
    }
}

    8.8.2. 示例：读者与写者

    考虑下面的示例：

    • 我们有一个数组，一些线程向其中写入数据（写者），另一些线程读取数据（读者）；
    • 写者彼此平等但互斥：一次只有一个写者可以向数组写入数据；
    • 读者彼此平等但互斥：一次只有一个读者可以读取数组中存储的数据；
    • 只有当写者在数组中放入了一些数据时，读者才能从数组中读取数据；只有当数组中已有的数据被读者读取之后，写者才能向数组中放入新的数据。

    有两种类型的共享资源：

    • 可写的表：一次只有一个写者可以访问它；
    • 只读的表：一次只有一个读者可以访问它。

    以及使用这些资源的顺序：

    • 读者必须总是跟在写者之后；
    • 写者必须总是跟在读者之后，第一次除外。

    可以使用两个 [Semaphore] 类型的屏障来控制对这两个资源的访问：

    • [canWrite] 屏障控制写者对数组的访问；
    • 屏障 [canRead] 控制读者对数组的访问；
    • [canWrite] 屏障以打开状态创建（一个许可），允许第一个写者通过，并阻塞所有其他写者；
    • [canRead] 屏障以关闭状态创建（没有许可），阻塞所有读者；
    • 当写者完成工作后，它打开屏障 [canRead] ，让一个读者进入；
    • 当读者完成工作后，它打开屏障 [canWrite] ，让一个写者进入。

    在这里我们看到了不属于任何线程的屏障的好处：屏障 [canRead] 由读者关闭（取走许可），由写者打开（归还许可）。这对于锁是不可能的，因为锁只能由持有它的线程释放。演示这种同步的程序 [Threads19.java] 如下：

static class Board {

    private static final int[] data = new int[3];
    // 表示可以读取 data 的内容：开始时关闭（没有许可）
    private static final Semaphore canRead = new Semaphore(0);
    // 表示可以写入 data：开始时打开（有一个许可）
    private static final Semaphore canWrite = new Semaphore(1);

    // 读取数组的内容
    static void read() {
        String name = Thread.currentThread().getName();
        IO.println("Method [read] started by thread " + name);
        // 我们等待读取许可
        canRead.acquireUninterruptibly();
        // 读取数组
        for (int i = 0; i < data.length; i++) {
            // 等待 0.5 秒：线程让出处理器
            sleep(500);
            IO.println(time() + " : reader " + name + " read the number " + data[i]);

        // 我们允许一个写者
        canWrite.release();
        IO.println("Method [read] finished by thread " + name);
    }

    // 写入数组
    static void write() {
        String name = Thread.currentThread().getName();
        IO.println("Method [write] started by thread " + name);
        // 我们等待写入许可
        canWrite.acquireUninterruptibly();
        // 写入数组
        for (int i = 0; i < data.length; i++) {
            // 等待 0.5 秒

        // 我们允许一个读者
        canRead.release();
        IO.println("Method [write] finished by thread " + name);
    }
}

    8.8.3. wait 和 notifyAll 方法

    在前面的示例中，当写者阻塞在指令 [canWrite.acquireUninterruptibly()] 上时，其中一个——任意一个——会被操作 [canWrite.release()] 解除阻塞。如果想为某个特定的写者打开屏障，事情就变得更复杂了。

    考虑一个有服务柜台的公共服务办事处的类比。顾客到达时，从取号机上取一张编号的号码票，然后去坐下。通过扬声器按号码叫顾客。等待期间，顾客可以做任何他们想做的事：可以看书，也可以打瞌睡。每当扬声器播报一个号码，他们就会被唤醒。如果是他们的号码，顾客就起身走向柜台；否则，他们就回去继续做原来的事。我们可以用类似的方式来处理线程。我们以写者为例：

    在柜台
    对于线程
    几位写者在等待同一个柜台
    它们的线程被阻塞
    柜台变得可用，并叫到下一位写者的号码
    从数组中读取数据的线程通知写者数组可用了。由该线程或另一个线程判定应由哪一个写者继续
    每位写者核对自己的号码；只有号码被叫到的那一位前往柜台；其余的回到等待队列
    每个线程检查自己是否是被选中的那一个。如果是，它就通过屏障；否则，它回到等待队列

    Java 允许您使用 每个对象都具备的方法来实现这个场景，因为这些方法定义在 [Object] 类中：

    方法
    作用
    [void wait()]

    我们现在来描述一种标准模式——尤其是 Brian Goetz 等人的著作 [Java Concurrency in Practice] 中介绍过的——它可以解决带有进入条件的屏障问题。

    共享资源（柜台）的线程通过一个我们称为 令牌的对象来访问它：它是一个简单的对象（[new Object()]），使用的是它的监视器。要穿过通往柜台的屏障，必须持有令牌，而令牌只有一个。因此，线程必须来回传递令牌。

    要前往柜台，线程首先使用 [synchronized (token)] 代码块请求令牌。如果它获得了令牌，就在循环 [while (!iAmTheExpectedOne) { token.wait(); }] 中检查自己是否满足前往柜台的条件，然后仍在 [synchronized] 代码块内前往柜台。如果该线程不是柜台所期待的那一个，它就通过 [token.wait()] 归还令牌，让出它的轮次，并进入阻塞状态。当另一个线程发出访问条件变更的信号时，它会被唤醒；随后它会取回令牌并再次检查条件。这就是为什么测试是循环（[while]） 而不是简单的 [if]。还有第二个原因，是 Java 特有的：规范允许出现“虚假唤醒”，即 [wait] 在没有任何线程调用 [notify] 的情况下结束；循环使这些虚假唤醒变得无害。操作 [token.wait()] 只能由持有令牌监视器的线程执行；否则会抛出 [IllegalMonitorStateException] 异常。在这种方案中，令牌只有在事务完成之后才会被释放。

    修改柜台访问条件的线程也必须持有令牌并通知等待中的线程：在 [synchronized (token)] 代码块内，它修改柜台的访问条件，然后使用 [token.notifyAll()] 唤醒等待中的线程。

    唤醒线程意味着等待中的线程成为令牌的候选者；它们不会立即得到令牌。令牌只有在 [synchronized] 代码块结束时才可用。随后，所有被唤醒的线程会依次、以不确定的顺序得到令牌，这让它们有机会再次检查访问条件。第一个满足条件的线程保留令牌，并前往队列。

static class Board {
    // 读者与写者之间共享的数组
    private static final int[] data = new int[3];
    // 读计数器和写计数器的访问令牌
    private static final Object canRead = new Object();
    private static final Object canWrite = new Object();
    // 计数器的访问条件
    private static boolean readingAllowed = false;
    private static boolean writingAllowed = false;
    private static int nextReader = 0;
    private static int nextWriter = 0;
    // 读者和写者的顺序
    static List<String> readOrder = List.of();
    static List<String> writeOrder = List.of();

    // 打开写计数器
    static void allowWriting() {
        synchronized (canWrite) {
            writingAllowed = true;
            // 我们唤醒所有等待令牌的写者
            canWrite.notifyAll();
        }
    }

    // 读取数组的内容
    static void read() {
        String name = Thread.currentThread().getName();
        IO.println("Method [read] started by thread " + name);
        // 我们请求读计数器的令牌
        synchronized (canRead) {
            try {
                // 只要还没轮到我们，就归还令牌并等待
                while (!readingAllowed || !readOrder.get(nextReader).equals(name)) {
                    canRead.wait();
                }
            } catch (InterruptedException e) {
                return;
            }
            // 在计数器处：读取数组
            for (int i = 0; i < data.length; i++) {
                sleep(500);
                IO.println(time() + " : reader " + name + " read the number " + data[i]);
            }
            // 下一个读者
            readingAllowed = false;
            nextReader++;
            // 我们通知写者可以写入了
            synchronized (canWrite) {
                writingAllowed = true;
                canWrite.notifyAll();
            }
            IO.println("Method [read] finished by thread " + name);
        }
    }

    // 写入数组
    static void write() {
        String name = Thread.currentThread().getName();
        IO.println("Method [write] started by thread " + name);
        // 我们请求写计数器的令牌
        synchronized (canWrite) {
            try {
                // 只要还没轮到我们，就归还令牌并等待
                while (!writingAllowed || !writeOrder.get(nextWriter).equals(name)) {
                    canWrite.wait();
                }
            } catch (InterruptedException e) {
                return;
            }
            // 在计数器处：写入数组
            for (int i = 0; i < data.length; i++) {
                sleep(500);
                data[i] = ThreadLocalRandom.current().nextInt(0, 1000);
                IO.println(time() + " : writer " + name + " wrote the number " + data[i]);
            }
            // 下一个写者
            writingAllowed = false;
            nextWriter++;
            // 我们通知读者可以读取了
            synchronized (canRead) {
                readingAllowed = true;
                canRead.notifyAll();
            }
            IO.println("Method [write] finished by thread " + name);
        }
    }
}

    • 第 78–81 行：读者修改写队列的访问条件，并通知所有等待的写者状态已发生变化。为此，它获取令牌 [canWrite]：这里可以看到该线程同时持有两个令牌。写者以相反的顺序做同样的事（它们持有 [canWrite] 并请求 [canRead]），这正是上文所述的死锁情形。不过这里没有风险：线程只在访问柜台结束时才请求第二个令牌，两个柜台绝不会同时被占用，而其他线程持有令牌的时间仅够检查访问条件，并不会请求另一个令牌。

    8.8.4. 条件：Condition 接口

        lock.readLock().lock();
        try {
            IO.println(time() + " : " + name + " starts reading the price of " + article);
            // 长时间读取
            sleep(1000);
            int p = prices.get(article);
            IO.println(time() + " : " + name + " read the price of " + article + " : " + p);
            return p;
        } finally {
            lock.readLock().unlock();
        }
    }

    // 写锁是独占的：没有读者，也没有其他写者
    void modify(String article, int newPrice) {
        String name = Thread.currentThread().getName();
        IO.println(time() + " : " + name + " requests the write lock");
        lock.writeLock().lock();
        try {
            IO.println(time() + " : " + name + " starts modifying the price of " + article);
            // 长时间写入
            sleep(1000);
            prices.put(article, newPrice);
            IO.println(time() + " : " + name + " set the price of " + article + " to " + newPrice);
        } finally {
            lock.writeLock().unlock();
        }
    }
}

    8.9. 并发集合

    前面的示例保护的都是非常简单的共享数据（一个计数器、一个数组、一个小字典）。当线程共享集合（列表、字典、队列）时，可以用锁保护每一次访问。然而，标准集合（[ArrayList]、[HashMap]、[ArrayDeque]）在设计上并不支持被多个线程同时修改：不加保护地使用可能导致元素丢失、引发意外的异常（[ConcurrentModificationException]），甚至破坏集合的内部结构。方法 [Collections.synchronizedList(…)]、[Collections.synchronizedMap(…)]…… 将普通集合包装成一个每个方法都是 [synchronized] 的对象：这是安全的，但所有线程都要竞争同一个锁，而且遍历集合时仍然必须手动加以保护。自 Java 5 起，[java.util.concurrent] 包提供了专为在线程间共享而设计、无需显式加锁的集合：

    8.9.2. 一个生产者和多个消费者：BlockingQueue

    读者和写者问题是经典生产者-消费者问题的一个变体：一些线程生产数据，另一些线程消费数据。[BlockingQueue<E>] 接口无需任何显式的同步工具即可解决这个问题：

    • [put(element)] 向队列添加一个元素。如果队列容量有限且已满，生产者将被阻塞，直到出现空位；
    • [take()] 移除队首的元素。如果队列为空，消费者将被阻塞，直到有元素到来；
    • [offer(element, timeout, unit)] 和 [poll(timeout, unit)] 的作用相同，但有最长等待时间；[offer(element)] 和 [poll()] 没有超时设置，从不阻塞：失败时它们返回 [false] 或 [null] 。

        }

    var consumers = new Thread[nbConsumers];
    for (int i = 0; i < consumers.length; i++) {
        consumers[i] = new Thread(() -> {

                    if (number == END) {
                        break;

                    IO.println(time() + " : " + name + " took " + number);
                    // 处理该数字
                    Thread.sleep(600);
                }
                IO.println(time() + " : " + name + " has finished");

                Thread.currentThread().interrupt();
            }
        }, "C" + (i + 1));
    }

    producer.start();
    for (Thread consumer : consumers) {
        consumer.start();

    8.10. 线程池：ExecutorService

    8.10.1. 原理

    到目前为止，为了管理线程，我们都是先创建它们，再通过 [start()] 启动。创建平台线程是一项相对昂贵的操作：特别是系统必须为它分配一个栈，而且每个线程在存在期间都会占用内存。我们将在第 10 章看到连接池的存在：已打开的连接被保留备用，并借给请求它们的线程，因为打开连接的代价很高。线程也有类似的机制：线程池。

    Java 使用 [java.util.concurrent.ExecutorService] 接口（“执行器”）来表示线程池：不再创建线程，而是把任务交给执行器，由它让自己的线程去执行。完成了一个任务的线程不会被销毁，而是继续处理下一个任务。[ThreadPoolExecutor] 类是最常见的实现，其工作方式如下：

    • 它拥有固定数量的线程（“核心池大小”）：只要尚未达到这个数量，每个新任务都会触发创建一个新线程；
    • 超出之后，任务被放入队列 （[BlockingQueue]），线程从中取出任务；
    • 如果队列已满，线程池会创建额外的线程，直到达到最大数量（“最大池大小”）。如果这些额外的线程空闲超过一定时间，就会被销毁；
    • 如果已达到最大值且队列已满，任务就会被拒绝：默认情况下，提交该任务的方法会抛出 [RejectedExecutionException] 异常。

    线程池有两个优点：它节省了创建线程所花的时间（几个线程就能处理数百个请求），并且通过限制线程数量，防止应用程序被过多的请求压垮。

    执行器通过其 [shutdown] 方法终止（它不再接受新任务，其线程在已提交的任务完成后停止），之后可以接着调用 [awaitTermination] （等待任务完成），或者通过 [shutdownNow] （中断正在执行的任务）终止。从 Java 19 起，[ExecutorService] 扩展了 [AutoCloseable] 接口：其 [close] 方法调用 [shutdown] ，然后等待所有任务完成。因此，你可以在带资源的 [try] 语句中声明执行器：退出该块时，所有已分配的任务都已完成。[Threads25.java] 程序如下：

    // 线程池的状态
    IO.println("%s : job no. %d starts in thread %s (threads: %d, active: %d, queued: %d)"
            .formatted(time(), data.number(), Thread.currentThread().getName(),
                    pool.getPoolSize(), pool.getActiveCount(), pool.getQueue().size()));
    // 休眠 [duration] 秒
    try {
        Thread.sleep(data.duration() * 1000L);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
    double duration = Duration.between(data.start(), LocalTime.now()).toMillis() / 1000.0;
    IO.println("%s : job no. %d ends: scheduled for %d s, it lasted %.2f s since its request"
            .formatted(time(), data.number(), data.duration(), duration));
}

void main() throws InterruptedException {
    IO.println("Main thread: " + Thread.currentThread());

    // 1 - 一个 2 个线程的线程池，在 try 块结束时自动关闭
    try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
        // 三个任务，每个都返回 Integer 类型的结果
        var futures = new ArrayList<Future<Integer>>();
        for (int i = 0; i < 3; i++) {
            int number = i;
            futures.add(pool.submit(() -> {
                IO.println(time() + " : task " + number + " runs in thread "
                        + Thread.currentThread().getName());
                // 工作：Callable 可以抛出受检异常
                Thread.sleep(500L * (number + 1));
                // 任务的结果
                return number * 10;
            }));
        }
        // 结果：get() 等待任务结束
        for (int i = 0; i < futures.size(); i++) {
            Future<Integer> future = futures.get(i);
            try {
                IO.println("task " + i + " : result " + future.get() + ", state " + future.state());
            } catch (ExecutionException e) {
                IO.println("task " + i + " failed: " + e.getCause());
            }
        }

        // 一个抛出异常的任务
        Future<Integer> failing = pool.submit(() -> fail());
        try {
            failing.get();
        } catch (ExecutionException e) {
            // 任务的异常被包装在 ExecutionException 中
            IO.println(e.getClass().getSimpleName() + " containing " + e.getCause().getClass().getSimpleName()
                    + " : " + e.getCause().getMessage());
        }
        IO.println("failing task: state " + failing.state());
    }

    // 2 - 每个任务一个虚拟线程；invokeAll 提交一个任务集合并等待它们结束
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        List<Callable<String>> jobs = new ArrayList<>();
        for (int i = 0; i < 3; i++) {
            int number = i;
            jobs.add(() -> {
                Thread.sleep(300);
                return "job " + number + " executed by " + Thread.currentThread();
            });
        }
        for (Future<String> future : executor.invokeAll(jobs)) {
            // 任务已结束：resultNow() 无需等待即可返回其结果
            IO.println(future.resultNow());
        }
    }
}

    long start = System.nanoTime();
    int nb = ForkJoinPool.commonPool().invoke(new CountPrimes(2, N));
    IO.println("common pool       : %,d prime numbers in %d ms".formatted(nb, since(start)));

    // 一个 4 个线程的线程池，在 try 块结束时关闭
    try (var pool = new ForkJoinPool(4)) {
        CountPrimes.chunks.clear();
        start = System.nanoTime();
        nb = pool.invoke(new CountPrimes(2, N));
        IO.println("pool of 4 threads : %,d prime numbers in %d ms".formatted(nb, since(start)));
        IO.println("tasks stolen by one thread from another: " + pool.getStealCount());
    }
    // 各数据块在最后一个线程池的各线程之间的分布
    new TreeMap<>(CountPrimes.chunks).forEach((name, nbChunks) ->
            IO.println("  %-25s : %d chunks processed".formatted(name, nbChunks)));
}

// 统计区间 [start, end[ 内素数个数的任务
static class CountPrimes extends RecursiveTask<Integer> {
    @Serial
    private static final long serialVersionUID = 1L;
    // 低于此阈值，数据块直接处理
    private static final int THRESHOLD = 100_000;
    // 每个线程处理的数据块数
    static final Map<String, Integer> chunks = new ConcurrentHashMap<>();

    private final int start;
    private final int end;

    CountPrimes(int start, int end) {
        this.start = start;
        this.end = end;
    }

    @Override
    protected Integer compute() {
        // 数据块足够小：我们按顺序处理
        if (end - start <= THRESHOLD) {
            chunks.merge(Thread.currentThread().getName(), 1, Integer::sum);
            int nb = 0;
            for (int i = start; i < end; i++) {
                if (isPrime(i)) {
                    nb++;
                }
            }
            return nb;
        }
        // 否则，我们将其一分为二
        int middle = (start + end) >>> 1;
        var left = new CountPrimes(start, middle);
        var right = new CountPrimes(middle, end);
        // 左半部分交给线程池（另一个线程可能会“窃取”它）
        left.fork();
        // 右半部分由当前线程处理
        int nbRight = right.compute();
        // 我们等待左半部分的结果，并合并两个结果
        return left.join() + nbRight;
    }
}

// 素性测试（刻意写得简单）
static boolean isPrime(int n) {
    if (n < 2) {
        return false;
    }
    for (int d = 2; d * d <= n; d++) {
        if (n % d == 0) {
            return false;
        }
    }
    return true;
}

// 自 [start] 起经过的毫秒数（以纳秒为单位）
static long since(long start) {
    return (System.nanoTime() - start) / 1_000_000;
}

    8.12. 线程本地数据

    8.12.1. 原理

    考虑一个三层应用程序：

    假设该应用程序是多用户的，例如一个 Web 应用程序。每个用户请求由一个线程处理。线程的生命周期如下：

    • 创建线程（虚拟线程），或从线程池中请求一个线程来满足用户的请求；
    • 如果该请求需要数据，线程就执行 [ui] 层中的一个方法，该方法调用 [business] 层中的一个方法，后者又调用 [dao] 层中的一个方法；
    • 线程把响应返回给用户。然后它要么终止，要么被归还给线程池。

    在第二步中，让线程拥有自己的数据（即不与其他线程共享的数据）可能会很有用。例如，这些数据可以属于该线程正在服务的特定用户，并在各个 [ui, business, dao] 层中使用，而无需作为参数传给每个方法。

    Java 为此提供了两种工具：

    • [ThreadLocal<T>] 类（Java 1.2）：一个对象，其值（由 [get()] 读取，由 [set(value)] 写入）对每个线程都是不同的。构造方法 [ThreadLocal.withInitial(supplier)] 为每个线程提供初始值；方法 [remove()] 清除当前线程的值。派生类 [InheritableThreadLocal<T>] 把创建线程持有的值传递给新创建的线程；
    • [ScopedValue<T>] 类（Java 25 中已定稿）：一个在代码的限定作用域内绑定到某个线程的值，并且在该作用域内不能被修改。

    8.12.3. ScopedValue 类

    [ScopedValue<T>] 值在一段代码的执行期间被绑定到某个值，这段代码称为它的作用域：

    • [ScopedValue.newInstance()] 创建一个可绑定的值，通常存储在 [static final] 字段中；
    • [ScopedValue.where(sv, value).run(action)] 通过把 [sv] 绑定到 [value] 来执行该操作（一个 [Runnable]）。在当前线程中执行该操作及其调用的所有方法期间，[sv.get()] 返回 [value]。操作结束时，绑定即消失：无需任何清理；
    • [ScopedValue.where(sv, value).call(op)] 对返回结果的操作做同样的事；
    • 在作用域内，值不能被修改；它只能在嵌套作用域中被绑定到另一个值；
    • [isBound()] 指示该值在当前线程中是否已绑定；[orElse(other)] 返回该值，如果未绑定，则返回 [other]。在任何作用域之外，[get()] 会抛出 [NoSuchElementException] 异常。

    private final Deque<Runnable> undos = new ArrayDeque<>();
    private final int number = counter.incrementAndGet();

    int getNumber() {
        return number;
    }

    // 记录撤销某次更新的操作
    void log(Runnable undo) {
        undos.push(undo);
    }

    // 提交事务：更新被保留
    void commit() {
        undos.clear();
    }

    // 回滚事务：更新被撤销，从最后一个到第一个
    void rollback() {
        Runnable undo;
        while ((undo = undos.poll()) != null) {
            undo.run();
        }
    }
}

    private final List<Article> table = new ArrayList<>();
    private final Object lock = new Object();
    private int nextId = 1;

    @Override
    public int insertArticle(Article article) {
        // 当前线程中是否有正在进行的事务？
        Transaction transaction = ThreadContext.transaction.get();
        synchronized (lock) {
            if (table.stream().anyMatch(a -> a.name().equals(article.name()))) {
                throw new IllegalStateException("an article named [" + article.name() + "] already exists");
            }
            Article inserted = new Article(nextId++, article.name(), article.price(),
                    article.currentStock(), article.minimumStock());
            table.add(inserted);
            // 在事务中，我们记录如何撤销插入
            if (transaction != null) {
                transaction.log(() -> {
                    synchronized (lock) {
                        table.remove(inserted);
                    }
                });
            }
            String mode = transaction == null
                    ? "outside a transaction"
                    : "in transaction " + transaction.getNumber();
            IO.println("[" + Thread.currentThread().getName() + "] [dao] insertion of " + inserted.name()
                    + " (id " + inserted.id() + ") " + mode);
            return 1;
        }
    }

    @Override
    public List<Article> getAllArticles() {
        synchronized (lock) {
            return List.copyOf(table);
        }
    }

    @Override
    public void deleteAllArticles() {
        synchronized (lock) {
            table.clear();
        }
    }
}

static class Business implements IBusiness {
    private final IDao dao;

    Business(IDao dao) {
        this.dao = dao;
    }

    // 插入商品列表：要么全部成功，要么全部失败
    @Override
    public void insertArticlesInTransaction(List<Article> articles) {
        // 事务开始，存储在线程局部数据中
        var transaction = new Transaction();
        ThreadContext.transaction.set(transaction);
        try {
            for (Article article : articles) {
                // [dao] 层将在线程中找到该事务
                dao.insertArticle(article);
                // 模拟处理，给其他线程留出介入的时间
                sleep(200);
            }
            transaction.commit();
            IO.println("[" + Thread.currentThread().getName() + "] [business] transaction "
                    + transaction.getNumber() + " committed");
        } catch (RuntimeException e) {
            transaction.rollback();
            IO.println("[" + Thread.currentThread().getName() + "] [business] transaction "
                    + transaction.getNumber() + " rolled back");
            // 异常被重新抛给调用者
            throw e;
        } finally {
            // 线程不再有正在进行的事务
            ThreadContext.transaction.remove();
        }
    }

    // 不使用事务插入商品列表
    @Override
    public void insertArticlesOutOfTransaction(List<Article> articles) {
        for (Article article : articles) {
            dao.insertArticle(article);
        }
    }

    @Override
    public List<Article> getAllArticles() {
        return dao.getAllArticles();
    }

    @Override
    public void deleteAllArticles() {
        dao.deleteAllArticles();
    }
}

    8.12.5. 结论

    前面的示例展示了线程本地数据在事务管理中的价值。不应完全照搬它的写法，但它准确地描述了框架的工作方式：Spring 的事务管理（[@Transactional] 注解）把事务和数据库连接放入 [ThreadLocal] 中，数据访问层查询它们，而代码本身无需操作事务；Hibernate 同样可以把工作会话与当前线程关联起来。我们将在第 11 章再回到这些工具。在新代码中，尤其是使用虚拟线程时，推荐用 *[ScopedValue]* 来传递这类上下文信息。
